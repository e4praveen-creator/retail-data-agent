## One working folder, clear responsibilities

The `Milky Way 2.0` directory contains the runnable application, source, tests, synthetic-data generator, domain methods and developer handbook. Keep the following boundaries when adding features or cleaning a checkout.

| Location, relative to Milky Way 2.0 | Responsibility | Retention rule |
|---|---|---|
| `retail_app/backend/` | Runtime API, agent, data access and workspace services | Source; review and test changes |
| `retail_app/frontend/` | React source and UI helpers | Source; rebuild after changes |
| `retail_app/scripts/` | Frontend build tooling | Source; used by the package build command |
| `retail_app/static/` | Deployable browser entry, styles and hashed chunks | Required runtime assets; keep with the application |
| `retail_app/tests/` | Offline regression suites and opt-in live harness | Source; run before release |
| `retail_app/knowledge/` | Authored domain content and evaluation cases | Source; preserve baseline cases and expected results |
| `retail_app/docs/developer/` | Canonical developer/admin handbook, reference snapshots and acceptance evidence | Source and release evidence; regenerate deliberately |
| `retail_app/docs/` outside `developer/` | Earlier architecture, domain/visual specifications and verification history | Retain existing links and runtime context dependencies |
| `retail-data-analyst/` and `retail_playbook_library.md` | Baseline playbook methods, recipes and visual contracts | Runtime context and tested methods |
| `retail_data/src/`, `sql/`, `docs/` | Synthetic-data generation, schema and contracts | Source; preserve reproducibility |
| `retail_data/data/` | Generated analytical warehouse and supporting data | Local data; never part of routine cleanup |
| `retail_app/state/` | Private chats, feedback, published workspace, evaluation history, logs and backups | Local persistent state; never part of routine cleanup |
| `.venv-runtime/`, `retail_app/node_modules/` | Installed Python/frontend dependencies | Local installation; retain while needed |
| `retail_app/tmp/` | Named disposable test outputs and any separately created temporary work | Only the explicit generated-file allowlist is cleaned |

The source project’s synced `sources/` directory is outside this app’s working copy and is read-only. Do not move shared or synced material into cleanup operations.

The earlier `architecture-reference.txt` and `MILKY_WAY_REFERENCE.md` files are actively indexed as design references. They are not interchangeable with the current architecture chapter and must not be removed as apparent duplicates. Current source and dated release evidence take precedence over historical proposals.

## Developer check command

From the **Milky Way 2.0 root**, with Node and pnpm on `PATH`:

```sh
.venv-runtime/bin/python -m retail_app.maintenance check
```

This is the canonical offline verification entry point. It runs these existing checks in order and stops on the first failure:

1. Installed Python dependency compatibility (`pip check`).
2. The full offline backend suite, which generates UI fixtures using isolated application state.
3. Frontend rendering and build-contract regression tests.
4. The production browser build.
5. Handbook links, generated JSON/SVG and recorded source fingerprints.

The command does not install dependencies or call a live model. Corepack network downloads are disabled for child commands. The test runner writes its normal quality receipt to `retail_app/state/eval_report.json`; it does not use the live chat database. Builds refresh the deployable static output. Run checks when no other process is editing or rebuilding the same checkout.

Individual stages are available when investigating a failure:

```sh
.venv-runtime/bin/python -m retail_app.maintenance check --target backend
.venv-runtime/bin/python -m retail_app.maintenance check --target frontend
.venv-runtime/bin/python -m retail_app.maintenance check --target docs
```

The frontend target requires the two fixture JSON files generated by the backend stage. A clean checkout or a checkout just cleaned with `clean --apply` needs the backend stage first. The full command handles that ordering automatically.

A stale documentation fingerprint is a failed check. It is not silently replaced to make verification green. After reviewing a source change, refresh the reference snapshots using `refresh_reference.py`, rebuild the handbook as described in [Testing](TESTING.md), then check again. Do not treat refreshed snapshots as a substitute for successful tests or review.

Offline checks do not establish live answer quality, browser layout acceptance or container acceptance. Those remain separate, explicitly recorded release activities. Generic hosted CI cannot run the current full warehouse suite from a source-only checkout: it needs the generated dataset and installed locked dependencies. A team runner with those prerequisites can use this same command without embedding credentials in its job configuration.

## Reproducible setup

The application Python lock is `retail_app/requirements.lock.txt`. Use a Python 3.12 environment as described in the root README. The frontend package metadata pins the package manager, and `pnpm-lock.yaml` locks dependency resolution. Install with `pnpm install --frozen-lockfile`; do not replace a lockfile with an unreviewed update during a routine build.

`retail_data/requirements.lock.txt` belongs to the separately versioned synthetic-data starter and includes its example API dependencies. Its DuckDB version is intentionally different from the application runtime. Use separate environments when regenerating the dataset with that kit, preserve the seed/configuration, and validate the resulting warehouse. The starter API is not the Milky Way production application.

`pip check` establishes installed dependency compatibility. It is not a vulnerability scan, license review or proof that fresh installation on another operating system has been tested. Record those checks separately when changing dependencies or preparing a new deployment platform.

## Safe cleanup

Preview only:

```sh
.venv-runtime/bin/python -m retail_app.maintenance clean
```

Remove the listed generated files:

```sh
.venv-runtime/bin/python -m retail_app.maintenance clean --apply
```

The command recognizes Python bytecode (`.pyc`/`.pyo`) and `.DS_Store` files in the three source trees, plus nine exact test/handbook output names in `retail_app/tmp/`. It does not treat everything in a directory named `tmp` as disposable.

The exact temporary-file allowlist is maintained in [`maintenance.py`](../../maintenance.py). If a build introduces another reproducible output, add that exact name and a regeneration instruction rather than broadening cleanup to arbitrary files or directories. Production hashed chunks are excluded from this cleanup policy; the build tool manages their publishing behavior.

Cleanup protection includes:

- Preview by default; deletion requires `--apply`.
- No directory recursion for deletion, and no traversal through symlinks.
- State, data, backups, dependencies, synced sources and production static assets are excluded.
- Hardlinked files are skipped.
- Each file’s identity, size and modification time are checked again before deletion. Replaced or changed files are skipped.
- Parent directories are opened with POSIX no-follow operations, so a parent changed to a symlink cannot redirect deletion outside the selected directory.
- Only an empty `__pycache__` directory is removed after its bytecode files are deleted. Unknown files within it remain.

The safety behavior is covered by [`test_maintenance.py`](../../tests/test_maintenance.py), including a parent-directory symlink swap after preview. The delete command requires POSIX directory operations; it fails rather than downgrading protection on unsupported platforms. Backup and validation remain separate commands.

Avoid `git clean -fdx`, deleting entire `tmp/` or `state/` directories, and removing installed dependencies just to shrink a working installation. Those operations erase files outside the safe regeneration contract.

## Backups and private state

The existing backup workflow remains:

```sh
.venv-runtime/bin/python -m retail_app.maintenance backup
```

It uses SQLite’s consistent backup API, includes committed WAL contents and verifies database integrity. Existing output files are never overwritten. The backup excludes the API key, warehouse and source code. Keep an independently protected backup according to the team’s retention policy; this repository’s cleanup command never applies that retention policy or deletes backups.
